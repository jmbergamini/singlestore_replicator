# Code guide

Author: John Bergamini

The package is `s2rebuild/`. Every module starts with `s2rebuild <module>: <purpose>.` and the author line, and every public function says what it issues. Every statement the kit sends passes a Guard first (`sqlutil.py`); `tests/test_guard.py` scans each module for statement words outside its reviewed allowance.

## Module map

- `cli.py`: the command line. Parses global and command flags, picks the run (`Invocation`), opens journals, logs and sessions, and dispatches to the step handlers or command functions. Every journal it opens is checked in one place (`Invocation.check_journals`: the recorded names, and the configuration hash after O1). `check` and `profile` apply the precondition and `--redo` rules of `steps.run_step` before they connect or write. `docs-flags` prints the flag table in `docs/CONFIG.md`.
- `common.py`: KitError and its exit codes, UTC time helpers, run ids.
- `config.py`: loads and validates the YAML against a declarative schema, applies defaults and the run-date names, refuses unknown keys, and exposes `Config`, `DatabaseSpec` and `Window` (with the abort deadline rule).
- `connect.py`: Secrets (Keychain or environment), the Redactor that masks secrets in every line (SQL user names are masked in logs only where they stand as a user, `mask_user`: user@host, a quoted account, USER = 'user', never inside a word or a label; they are kept in the admin blocks an operator copies), guarded `Session`, `DryRunSession` and `SessionFactory`, the 0600 `Log` (`Log.file` writes a line to the file only), `KeepAlive` (the daemon thread `steps.run_step` starts around every live step: `SELECT 1` on its own runner connection every `workspace.keepalive_minutes`, behind a read guard, opened at the first ping, failures logged and never raised) and `is_driver_error` (2003, 2004, 2006, 2013: the command line prints one plain line, exits 2 and sends the raw error to the log file).
- `workspace.py`: the Management API client over urllib (`Client.get`, the key as a bearer token, errors without the key) and the workspace guards: `read_workspace` (P2 with `workspace.management_api_key_keychain`: `GET /v1/workspaces/<workspace.id>`, the state, autoscale and auto-suspend in the preflight record, the raw fields kept because the field names are a best guess until I4), `preflight_lines` (state FAILED unless ACTIVE), `question_lines` (the three questions without a key), `plan_lines` (the plan sheet), `recorded` (the facts from the journal) and `o1_guard` (autoscale on refuses unless `--accept-autoscale NOTE`; `--workspace NOTE` recorded as evidence). Tests replace `default_transport`; nothing reaches the network.
- `journal.py`: the SQLite journal per run and database (WAL, synchronous FULL, one lock): meta, steps, tables, chunks, verification, attachments (the whole branch record per role: name, STORAGE_ID, COMPUTE_ID, attach type, record type, ATTACH_SYNTAX, detached; `record_attachment_row` takes a row of either attachment view or an `identify` record, and a row completes the latest row of the same record), grants snapshot, pipelines, offsets, events; schema migrations (version 4: the sample predicate and rows on verification rows); read-only and in-memory copies.
- `sqlutil.py`: identifier quoting, the statement classifier, the Guard (statement kinds and the databases they may name), SQL literals for injected secrets and the forms a secret can take in an error message.
- `steps.py`: the registry of P1 to C4 with kinds, identities, gates and preconditions; the owner allowances per step; `run_step` (with `start_keepalive` around the handler), `run_steps` and gate recording; O1 (`o1_start`) with its readiness checks and the workspace guard. Modules register their handlers here.
- `inventory.py`: P2 preflight (`preflight`, plus `workspace_check` through `workspace.py`) and the P3 and O4 capture (tables, keys, sizes, sessions, views; with the owner session the write-capable accounts, the pipelines with the credentials placeholder and the routines through `routines.py`; a reference table marked `reference` and counted with `COUNT(*)`, since `TABLE_STATISTICS` reports no rows for it), the copy plan (`TablePlan`, hash buckets; one bucket and `copy_path` staging for a reference table), drift (routines added, removed or changed, and pipelines added, removed or redefined, included; `pipeline_drift` compares nothing and leaves a note when a capture holds no pipeline listing, as the O4 capture of a READ ONLY source does).
- `routines.py`: functions, table-valued functions, aggregates and procedures. `capture` reads `information_schema.ROUTINES`, `SHOW AGGREGATES` and the three `SHOW CREATE` forms through the owner session (the runner sees no routine, fact 21) and each definition goes to `definitions/routines/<name>.<kind>.sql`; `place` creates them in the replacement in order (functions and TVFs, then aggregates at O5 after the tables; procedures at O7 after the views) in rounds, with the definer policy of the views (`postcopy.definer_choice`, the 1227 fallback recorded per routine), and `verify` is the gate per kind: every routine present and its normalized definition equal to the capture; the ROUTINES count the O7 gate records is what S3 expects on the live name. `objects.routines.ignore` leaves a routine behind (`split`, `summary` for the plan sheet); a load target INTO PROCEDURE the replacement will not hold refuses P3 and O4 (`refuse_pipeline_targets`); a body naming the source database refuses O5 or O7 before any statement.
- `estimate.py`: the throughput model (`chunk_seconds`; `reference_seconds` for a reference table, one chunk with its rows inserted twice), the list-scheduling simulation, allowances, bands, window fit, and `calibrate`.
- `report_xlsx.py` and `report_md.py`: the profile and final workbooks (Summary first, one tab per table, pipelines and offsets tabs) and the Markdown run report; the C2 handler.
- `transform.py`: the replacement definition hook (a pass-through in this pass; see below).
- `copy.py`: O5 and O6: the replacement, the chunk scheduler, reconciliation, lock probes, the fresh-table fallback, the abort deadline and stop file, the count proof, the copy lock that O6, an O7 re-copy round, `mark-recopy` and O10 take, the 1997 transient (`is_commit_phase`, `Runner.requeue_transient`: reconciled and requeued without an attempt) and the circuit breaker (`copy.max_consecutive_failures` failures in a row set `breaker_tripped`, no new chunk starts, O6 ends INCOMPLETE with `BREAKER_MESSAGE`).
- `verify.py` and `postcopy.py`: the three verification tiers and the O7 stale check, views and counters, the O8 handler. Tier 3 (`Verifier.tier3_all`) runs on `verify.sessions` worker threads with a runner connection each, largest table first with both sides of a table at once, under the `verify.fingerprint_budget_minutes` deadline; a table over `verify.full_fingerprint_max_rows` is sampled as a range on its first sort key column or its time column (`range_column`, `sampling`, `range_predicate`), and the value hash takes the time column plus `verify.value_columns` supported columns (`value_columns_for`). `recorded_state`, `tables_to_accept` and `accept_recorded` are the `--yes` acceptance without a rerun; `Verifier.rerun` serves `step O8 --fingerprint TABLE --percent N` and `--full TABLE`.
- `watch.py`: the writer watch and the quiet proof.
- `ownersql.py`: admin blocks (checks, statements, stops, skip conditions, captures) and their companion blocks (the O3 re-entry block, the O10 rollback through the retained copy, the C3 repair block), their execution with gates, the DETACH escalation, the P1 and C4 account blocks, the C3 End state block (`endstate_block`: the two-entry gate as reads, the write probe on the retained name through the runner) and its repair (`repair_block` for the hand route, `SwitchMachine.repair_end_state` for the kit route, after `ask` returns proceed), and `ownerlib`, the dependency-free copy of the gate logic for the notebook.
- `freeze.py`: O3 Path A with the write probe and the resume paths (after the READONLY attachment, and at the ATTACH after a stop between DETACH and ATTACH).
- `abandon.py`: the abandon command, a run backed out before O10 (source READWRITE again, replacement dropped, run closed).
- `cleanup.py`: the `cleanup` command (C5): the listing of what a run left after C3 (records, size, `retain_until_utc`), and `--delete NAME`, the customer's delete of the retained copy by its record after the date and after the name is typed at the prompt (`cleanup.ask`, replaced by tests): DETACH, the record's own ATTACH_SYNTAX read write, a record check, DROP, each behind its check, through the `cleanup` owner allowance. Every refusal and a mismatched name are journal events with exit 0; no step and no configuration key deletes the retained copy.
- `lockout.py` and `grants.py`: O3 Path B: per-scope snapshots, revoke, the kill loop, restore and compare.
- `pipelines.py`: O2 stop and capture, O9 replay or verification, O11 release, C1 checks, and the import of a notebook capture.
- `switch.py`: the O10 state machine (S1, S2, S2b, S3, S4 and the two-entry gate, `listing` recorded before and after) and the rollback (R1, then R2a by the original's syntax before S2b ran, R2b a branch of the retained copy after it, R2c when the server refuses a branch of a READ ONLY attachment), and the identity of a database: `identify(session, name)` joins MV_CLOUD_BRANCHES with MV_CLOUD_ATTACHED_DATABASES into one record, `records_match` compares the key (name, STORAGE_ID, ATTACH_TYPE, COMPUTE_ID), `refusal_text` prints both records; every DETACH, ATTACH and DROP of the machine, the rollback, the C3 repair and abandon runs behind that comparison. `Position.state` reads the position from the views, including the original attached read write (after S2b's attach or R2a), the original record dropped, the switch complete and a rollback through the retained copy.
- `notebook.py`: fills `notebooks/owner-steps.template.ipynb` with the run, the blocks and ownerlib.
- `rehearse.py`: P5 on throwaway databases with the SIGKILL test.
- `bundle.py`: MANIFEST.json, the static-tree scan, the zip and `--verify`.
- `enginecapture.py`: the `engine-capture` command: the engine version, the column list of every `information_schema` view the kit reads, SHOW AGGREGATES, the PASSWORD_ variables, the ATTACH forms and id shapes as patterns, the runner-versus-owner row counts on a fixture database, and the hand-maintained error table, written to `tests/engine/helios-<version>.json` for the test fake. Reads only.

`tests/fakedb.py` is an in-memory stand-in for the workspace built from the engine capture (attachments and branch records, pipelines that move with their record, grants by scope, identity rules, read-only refusals, lock waits, blocking DETACH, the capture reads of P3 and O4). `tests.helpers.fake_driver` puts it behind the driver, so a test can run a live command on the command line. Tests never open a network connection.

## The engine capture

The fake agrees with the engine through `tests/engine/helios-<version>.json`. Column lists come from the file: a query that names a column the capture does not list fails with error 1054, as the server would, and `tests/test_engine.py` checks every `information_schema` query the kit holds against it. Error texts come from its error table (`FakeDB.error`). The four Helios flags of the fake default on (`refuse_other_definer`, `refuse_sharded_counter`, `branch_keeps_storage_id`, `refuse_read_only_drop`); a test turns one off only to exercise the path an engine without that restriction would take, and says so in a comment. Branch records follow `MV_CLOUD_BRANCHES`: one row per record with DATABASE_NAME, STORAGE_ID, ATTACH_TYPE (create, resume, pitr), LATEST_COMPUTE_ID, IS_DETACHED, IS_DROPPED, END_VERSION and ATTACH_SYNTAX in its three forms; ROW_NUMBER is renumbered on every listing, so no kit code can key on it; `portal_entries()` is the Portal's list (IS_DROPPED = 0).

Refresh the capture per engine version:

1. On a workspace with the owner profile configured, run `s2rebuild engine-capture --fixture-database NAME`, where NAME is a database with at least one routine and one pipeline. It writes `tests/engine/helios-<version>.json` and prints the view count and the runner-versus-owner counts. Pass: every view has columns and no warning line. Fail: a warning names a view without columns; add them by hand from `SELECT * ... LIMIT 1` and keep the `seeded` note.
2. The error table (`enginecapture.ERROR_TABLE`) is kept by hand and carried over from the existing file; add a row when a live run shows a new error number, with the text the server gave.
3. Point the fake at the new file (`DEFAULT_CAPTURE` in `tests/fakedb.py`) and run the suite. Pass: `test_engine` and the suite pass. Fail: a 1054 names the column a view lost or renamed; fix the query, then the docs (a Helios fact in `docs/LESSONS.md` and section 11 of the architecture).

The 10.8.0 file is seeded by hand from the kit's queries (its `seeded` field says so and `captured` is null); the first live `engine-capture` replaces it.

## Data flow

1. `config.yaml` becomes a `Config`; each configured database a `DatabaseSpec` with its replacement and retained names.
2. P3 writes the inventory under `customer/runs/<run>/<db>/inventory/P3/`; O4 writes it again after the freeze. The copy plan comes from the newest capture.
3. Every step writes its start, end, outcome and evidence to `journal.sqlite`; the copy writes each chunk transition before the statement it guards; admin blocks write each check and statement as events; P2, O3, O5 and the switch record branch records as attachments (a check with a record role stores its first row; the attachment row and the branch row of one record complete each other).
4. Reports read the capture and the journal: the profile workbook at P3, the final workbook and run report at O8 and C2. `calibrate` reads the chunk timings back into `customer/baseline.json`.

## Adding a step or a statement

1. Add the step to `REGISTRY` in `steps.py` with its gate and preconditions.
2. Write the handler in the module that owns the work and call `steps.register(ID, handler)` at the bottom of that module.
3. An owner statement goes into a `Block` with a check before and after it; add its kind to the step's entry in `OWNER_ALLOWANCES` and teach `sqlutil.classify` the statement shape if it is new.
4. Add the statement words to the module's entry in `tests/test_guard.py` with a reason, and a test on the fake.

## Decisions you can change

| Decision | Current choice | Alternative and where |
|---|---|---|
| Replacement definition | Partition layout only; `transform.apply` is a pass-through | Fill in `transform.py` for keys, indexes, storage, renames; the hook, config keys and report block exist |
| Chunking strategy | Hash buckets, `CRC32(key) MOD B`, complete coverage by construction | Range chunking on a sort-key prefix for multi-billion-row tables: a `RangePlan` in `copy.py` with NULL and open-ended buckets and a coverage test |
| Bucket cap | 32 per table | Raise for restart granularity, lower for scan cost: `copy.max_buckets_per_table` |
| Freeze default | Read-only attachment | `freeze.mode: lockout`; the lockout loop also serves as a bridge during a slow detach |
| Switch order | Retained branch first, then the original record dropped (S2b), then live, then the replacement dropped (S4) | Live first saves one step; the current order keeps the live name unambiguous and ends with two entries |
| Replacement after switch | Dropped at S4 by its record, after S3's checks | Leave it attached and drop it in the close-out: one more entry on the workspace and a DROP outside the window |
| Retained copy | Kept until the customer runs `cleanup --delete` after `retain_until_utc`, typing the name twice | A configured retention that deletes it from a step: rejected on purpose; the copy is the way back |
| Verification depth | Count, newest, grouped fingerprint; a table over `verify.full_fingerprint_max_rows` sampled as a range on its sort key or time column | Full fingerprint everywhere (`verify.full_fingerprint_max_rows` above the largest table, or `step O8 --full TABLE`) or counts only |
| View definers | Created by the owner session; the original DEFINER kept while its account exists and is not the runner, else the owner account; without the owner profile the O7 block for the admin | Always the owner account, or a named service account: `postcopy.definer_choice` |
| Routine definers and order | The view policy through the owner session; functions and TVFs, then aggregates at O5, procedures at O7, each kind in rounds | A dependency order read from the bodies, or every routine at O7: `routines.O5_KINDS` and `routines.O7_KINDS` |
| Counters | The larger of the source counter and MAX + 1, then sync on every aggregator (ALL) | MAX + 1 only, or the source counter only: `postcopy.counter_value` |
| Admin steps | Execute with gates when the owner profile exists | Print only (no owner profile) or the generated notebook |
| Workers | 4 | Up to 16; watch leaf CPU: `copy.workers` |
| Driver | PyMySQL in the terminal, singlestoredb in the notebook | Either everywhere: `connect.py` and the notebook template |
| Secrets | Keychain or environment | A secrets manager: `connect.py` |
| Pipelines | Route kit: credentials from the environment at O9 | Route customer: the customer runs the placeholder file, the kit verifies: `pipelines.route` |
| Pipeline start position | Recorded offsets from O2 | EARLIEST or LATEST for a pipeline past retention: edit its ALTER statement in the capture and record the decision in the gate note |

## The transform hook

`transform.py` is where a later pass changes the replacement beyond its partition layout. Today `databases[].target.transforms` must be empty and `transform.apply` returns each table definition unchanged; the final report already carries an "original versus target definition" block. The ordered list of later-pass items is in the module docstring. A transform must keep the copy's column list valid and its definition diff explainable, and it must come with tests on the fake.
