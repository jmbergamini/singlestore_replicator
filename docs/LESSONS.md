# Lessons

Author: John Bergamini

The facts the kit relies on, in plain words, and what a real rebuild night taught. Each lesson names the design rule it produced.

## Helios facts

1. A database's partition layout is fixed at CREATE DATABASE. Sub-partitions cannot be added later, so a new layout means a new database and a copy.
2. ATTACH DATABASE takes a name, an optional new name (AS), READ ONLY, then an optional STORAGEID and COMPUTEID, the ids unquoted. AS creates a branch with its own STORAGE_ID. When two databases could share a name, only the STORAGE_ID tells them apart.
3. DETACH DATABASE waits while writers are active. DETACH ... KILL ends the blocking work and detaches after the upload. DETACH ... FORCE can lose unsynced data; the kit never uses it.
4. A database has one read-write attachment and may have several read-only ones. DETACH followed by ATTACH ... READ ONLY stops every writer, for every account, within minutes. The Portal does the same.
5. MV_CLOUD_BRANCHES lists every storage with its STORAGE_ID and whether it is detached. Its database names are not unique.
6. A branch and its parent are independent: dropping one leaves the other intact.
7. The Management API has no attach, detach, branch or read-only operation. Admin SQL or the Portal is the path.
8. CREATE DATABASE and DROP DATABASE are privileges of their own; CREATE and DROP do not cover them.
9. SUPER cannot be granted. SHOW CREATE PIPELINE ... EXTENDED returns the definition, the CONFIG and the ALTER PIPELINE ... SET OFFSETS and SET OFFSET CURSOR statements as extra rows, but hides CREDENTIALS from every identity, the workspace owner included.
10. An account without pipeline privileges sees no pipelines at all. Without PROCESS an account sees only its own sessions.
11. A global REVOKE applies to new connections only. Existing sessions keep their rights until they are killed. KILL CONNECTION reaches only the aggregator the killer is connected to.
12. A client killed in the middle of an INSERT leaves a prepared transaction holding a leaf table lock for 15 to 20 minutes. No process list shows it and no SQL statement clears it.
13. Inserting millions of rows into a columnstore table with a large varchar unique key takes a table-level lock on the leaf. Parallel chunks into such a table collide with error 1205.
14. CREATE TABLE ... LIKE copies the AUTO_INCREMENT attribute but not the counter. AGGREGATOR SYNC AUTO_INCREMENT syncs the counter after it is set.
15. TABLES.DATA_LENGTH is zero on Helios. Table size comes from MV_COLUMNSTORE_FILES joined to TABLE_STATISTICS on the leaf master partitions.
16. Attaching needs compute cores times 8 at or above the partition count.
17. query_parallelism_per_leaf_core is global, applies only to databases with sub-partitions, and is picked up by new connections.
18. Reference throughput with 4 workers on an S-16 at 2x: 13.1 million rows scanned and 339 thousand rows inserted per second per worker; 1.43 billion rows and about 490 GiB per hour in aggregate.
19. Engine 10.8.0, October 26, 2026: PIPELINES_BATCHES_SUMMARY has START_TIME (the batch timestamp), BATCH_TIME (the batch duration in seconds), ROWS_INSERTED and ROWS_UPDATED, and no BATCH_ROWS_WRITTEN. PIPELINES_ERRORS has ERROR_UNIX_TIMESTAMP and no ERROR_TIME.
20. Engine 10.8.0, October 26, 2026: a workspace can enforce a password policy (GLOBAL_VARIABLES PASSWORD_MIN_LENGTH, PASSWORD_MIN_UPPERCASE_CHARS and the other PASSWORD_ variables; on the test workspace a minimum length of 14, one of each character class, at most 3 repeated and 2 sequential characters). CREATE USER with a password that misses it fails with error 1144. P1 reads the policy through the owner session, prints it and generates the runner password to it (32 characters or the policy minimum, every class, no character twice in a row, no three sequential characters), so no password is typed or printed.
21. Engine 10.8.0, October 26, 2026: an account without routine privileges sees no rows in information_schema.ROUTINES; the owner sees them all.
22. Engine 10.8.0, October 26, 2026: ATTACH takes the STORAGEID unquoted and READ ONLY before it: ATTACH DATABASE x [AS y] [READ ONLY] [STORAGEID id]. A quoted id, or READ ONLY after STORAGEID, is error 1064. MV_CLOUD_BRANCHES.ATTACH_SYNTAX shows the form for each storage.
23. Engine 10.8.0, October 26, 2026: on a READ ONLY attachment information_schema.PIPELINES shows no rows, while PIPELINES_OFFSETS keeps them. Pipelines must be captured before the freeze.
24. Engine 10.8.0, October 27, 2026: an INSERT into a REFERENCE table runs on the master aggregator, and there a READ ONLY source has no master instance: `INSERT INTO new.ref SELECT ... FROM frozen.ref` fails with error 1777 ("Partitions of <db> has no master instance"). TABLE_STATISTICS shows no rows for reference tables. The copy stages each reference table through a sharded table in the replacement.
25. Engine 10.8.0, October 27, 2026: even the workspace admin cannot name another account as a view's DEFINER; CREATE VIEW with DEFINER=`other`@`%` fails with error 1227 (SUPER needed, and SUPER cannot be granted). O7 then creates the view without the clause, so the owner account is the definer.
26. Engine 10.8.0, October 27, 2026: ALTER TABLE ... AUTO_INCREMENT = X on a sharded table fails with error 1749 (not supported). Sharded counters carry the aggregator id, so a source counter cannot be carried over; AGGREGATOR SYNC AUTO_INCREMENT ON db.table ALL moves every aggregator past MAX.
27. Engine 10.8.0, October 27, 2026: `ATTACH DATABASE x AS y STORAGEID <x's id>` while x is attached keeps x's STORAGE_ID for y. y is still its own branch: writes through one name do not reach the other, DETACH or DROP of x leaves y attached with its data, and MV_CLOUD_BRANCHES shows y with its own COMPUTE_ID, ATTACH_TYPE pitr, PREV_DATABASE_NAME x and ATTACH_SOURCE_TIME. A database is identified by its branch record, name, STORAGE_ID and ATTACH_TYPE, never by STORAGE_ID alone, never by ROW_NUMBER (fact 33) and never by COMPUTE_ID (fact 44).
28. Engine 10.8.0, October 27, 2026: a database attached READ ONLY cannot be dropped (error 2720). Detach it and attach it read write first. A detached record cannot be dropped either. The test fake refuses both the same way. No step drops the retained copy; the customer's `s2rebuild cleanup --delete` runs detach, re-attach by syntax read write, drop, after the retention date and after the name is typed twice.
29. Engine 10.8.0, October 27, 2026: a detached record re-attaches exactly by its own ATTACH_SYNTAX from MV_CLOUD_BRANCHES, `ATTACH DATABASE <name> AT MILESTONE 'YYYY-MM-DD HH_MM_SS.ffffff' STORAGEID <id> COMPUTEID <id>`, read write (or READ ONLY before AT MILESTONE) under its own name; ATTACH ... AS from it makes a new resume record instead. A dropped record shows the `ATTACH DROPPED DATABASE` form. The kit classifies all three forms as ATTACH DATABASE. The switch records the detached original's syntax at S1 and the rollback re-attaches it by that syntax at R2.
30. Engine 10.8.0, Portal, October 27, 2026: after a switch the Portal lists four entries for two storages: the live name twice (the detached original and the live branch), the replacement and the retained copy. The detached original shows "Another database with this name is already attached" when selected. The kit names it by its record (name, STORAGE_ID, ATTACH_TYPE, COMPUTE_ID) and never deletes it in the Portal by STORAGE_ID, which the retained copy shares.
31. Engine 10.8.0, Portal, October 27, 2026: the retained copy appears in the Portal as "Read Only Legacy"; its MV_CLOUD_ATTACHED_DATABASES row says READONLY. Whether a newer read-only attach type exists is an open question for SingleStore.
32. Engine 10.8.0, October 27, 2026: dropping the record a `resume` branch continues from leaves that branch whole: every row present, and it survives a detach and a read-only re-attach. The switch relies on it at S2b (the original record dropped once the retained copy exists) and at S4 (the replacement dropped once the live branch exists); abandon still refuses to drop a replacement that has a branch.
33. Engine 10.8.0, October 27, 2026: ROW_NUMBER in MV_CLOUD_BRANCHES is not stable between listings. Identify a record by name, STORAGE_ID and ATTACH_TYPE (COMPUTE_ID changes on every attach, fact 44); the kit never reads ROW_NUMBER.
34. Engine 10.8.0, October 27, 2026: detach of the live name, attach of the original record by syntax, drop, and re-attach of the live record took about 30 seconds on tpcds3tb (3 TB). O10 S2b runs the attach, the proof and the drop while the live name is free, so the switch needs no second outage; C3 keeps the whole sequence as the repair block for a switch made without S2b and S4, and the rollback R2a runs the same attach by syntax.
35. Engine 10.8.0, October 27, 2026: the Portal's database list is the MV_CLOUD_BRANCHES rows with IS_DROPPED = 0, attached or detached; a dropped record leaves it and shows the ATTACH DROPPED DATABASE form. After the two-entry switch the list holds the live database and the retained copy only; the dropped original record and replacement stay recoverable with that form for the engine's retention period. I0b (October 28, 2026) found it accepted: `ATTACH DATABASE <retained> AS <source> STORAGEID <original>` from the READ ONLY retained copy gives a READWRITE pitr record under the live name with PREV_DATABASE_NAME the retained name and the original rows, and the retained copy stays READ ONLY with its rows. R2b is the rollback after S2b; R2c stays as the fallback on a refusal and was not needed.
36. Engine 10.8.0, October 27, 2026: `information_schema.TABLE_STATISTICS` reports no rows for a reference table, so a row estimate from it is 0 for every reference table and a plan built on it has no rows to schedule. The capture (P3 and O4) marks each `CREATE [ROWSTORE] REFERENCE TABLE` as `reference` and counts it with `SELECT COUNT(*)` whether or not `--exact-counts` is set; the plan gives it one bucket on the staging path, the estimate charges its rows at the insert rate twice, and `tables.csv` and the table tab say so. The test fake answers TABLE_STATISTICS the same way.
37. Engine 10.8.0, October 27, 2026: the runner sees no routine (fact 21) and no other account's grants, so the kit reads routines and the write-capable account list with the owner session: `information_schema.ROUTINES` (with its DEFINER column) for functions, table-valued functions and procedures, `SHOW AGGREGATES` in the database for the aggregates, then `SHOW CREATE FUNCTION`, `SHOW CREATE AGGREGATE` or `SHOW CREATE PROCEDURE` per routine. Without the owner profile P2 prints "routines: not visible to the runner; owner profile needed" and never "none". The replacement gets them in dependency order (functions and TVFs, then aggregates, at O5; procedures after the views at O7), so an aggregate finds its functions, a procedure finds its view and a pipeline INTO PROCEDURE at O9 finds its target.
38. Engine 10.8.0, Portal, October 27, 2026: the Portal's table list may show 0 rows for the tables of a database attached READ ONLY (it reads the statistics of the read-write attachment, which the frozen source no longer has). The rows are there: the kit's counts, taken through its own session and recorded in the journal and the O4 capture, are the reference, and O3 says so in its log. On Path A the O4 capture does not list PIPELINES either (fact 23): it records that the view is empty on a READ ONLY attachment and that O9 replays the O2 capture, so the drift report never shows every pipeline removed.
39. Engine 10.8.0, tpcds3tb, October 27, 2026: a sampled fingerprint written as CRC32(key) MOD 100 < 5 still read every row of the table, so the sample cost as much as the full fingerprint, and one session fingerprinted one side of one table at a time: accepting the sampled result reran every tier for 26 minutes. Tier 3 now runs on verify.sessions connections, largest table first with its source and replacement sides at the same time; a table over verify.full_fingerprint_max_rows is sampled as a contiguous range on its first sort key column or its time column (MIN and MAX read from the source, the same predicate on both sides, so segment elimination skips the rest), the report shows the predicate and the rows; step O8 --yes accepts the recorded result without a rerun when no chunk was copied since the last run; verify.fingerprint_budget_minutes is an elapsed deadline.
40. Helios, run 20261026-1301, October 26, 2026: autoscale replaces nodes one at a time (MV_EVENTS: SYSTEM_VAR_CHANGED, NEW_MASTER_AGGREGATOR, NODE_DETACHED, NODE_OFFLINE per leaf). Every chunk in flight fails with error 1997 "transaction was already in its commit phase"; 28 chunks were lost that way, and P3 once failed at a connection reset while the workspace was scaling. Run with autoscale off. P2 reads the setting through the Management API when `workspace.management_api_key_keychain` is set, and O1 refuses while it is on unless `--accept-autoscale NOTE` records the override. The copy treats 1997 as a transient (reconciled and requeued without consuming an attempt), `copy.max_consecutive_failures` chunk failures in a row trip the circuit breaker (no new chunk, O6 INCOMPLETE, rerun with `--retry-failed` when the workspace is steady), and a driver reset (2003, 2004, 2006, 2013) ends a command with one plain line, exit 2 and the raw error in the log file.
41. Helios, October 25, 2026: auto-suspend counts queries from connections as activity, not load batches; the workspace suspended while loads ran with no connection open. While a step runs, the kit's own keep-alive thread sends `SELECT 1` on its own runner connection every `workspace.keepalive_minutes` (default 15; 0 disables). Between commands nothing runs, so P4 records the choice: auto-suspend off for the window, or a notebook job of the customer that runs the same query every 15 minutes. To be confirmed in I4: the Management API field names the kit reads from `GET /v1/workspaces/<id>` are a best guess, `state` (ACTIVE expected), `autoSuspend` (a mapping with `suspendType`, DISABLED meaning off) and `autoScale` (a mapping with `enabled` or `maxScaleFactor`, above 1 meaning on); P2 records the raw fields, so a wrong name shows as "not reported".
42. Helios, S-8 at 4X (240 leaf cores), tpcds3tb, October 27, 2026: 270 M row chunks into 16 partitions took about 18 minutes at 4 workers (3.5 B rows per hour, leaf CPU about 17 percent) and 50 to 53 minutes at 12 workers (3.7 B rows per hour, CPU about 26 percent). Client concurrency is not the limit; the workspace is. So `customer/baseline.json` records the leaf cores of the workspace it was fitted on, P2 reads the leaf cores of the workspace in hand from `MV_NODES`, and the estimate scales its scan and insert rates by the ratio: downward without limit, upward at most `estimate.scale_up_cap` (default 1.0, no credit for a larger workspace until a performance test shows more). The plan sheet's planning line says what was applied and repeats this fact.
43. Engine 10.8.0, a 3 TB database, October 27, 2026: DETACH of the idle database took 73 seconds at O3 and 10 seconds on abandon; ATTACH READWRITE took 8 seconds. So `freeze.detach_wait_seconds` (default 120) is above the idle detach time, the escalation to DETACH ... KILL is for a database with writers, the estimate's freeze allowance of 10 minutes covers O3, and the 30 seconds of fact 34 are a sequence of four such statements with the live name free.
44. Engine 10.8.0, October 27, 2026 (I0b): every attach gives a record a new COMPUTE_ID, a re-attach of the same record by its own ATTACH_SYNTAX included: the original record detached at S1 with COMPUTE_ID ...:4008 came back at S2b as the same `create` row, READWRITE, with ...:4014, and its ATTACH_SYNTAX became the plain `ATTACH DATABASE <name> STORAGEID <id> COMPUTEID <new id>` form. The COMPUTEID inside a detached record's syntax equals its LATEST_COMPUTE_ID, the AT MILESTONE value has the form `YYYY-MM-DD HH_MM_SS.ffffff`, and the name is in backticks. So the kit identifies a record by name, STORAGE_ID and ATTACH_TYPE, never by COMPUTE_ID, which it records for the report only; the state checks after a DROP or DETACH read the records of the name on the storage, a record not dropped first. I0b also confirmed: a detached record re-attaches by the plain `ATTACH DATABASE <name> STORAGEID <id>` (the same record, read write), `READ ONLY` before `AT MILESTONE` attaches it read only, DROP DATABASE of a detached record fails with 1008 ("database doesn't exist"), and an INSERT on a READ ONLY attachment can fail with 2719 ("attached as a readonly database"), which the write probe accepts by its message.

## Run lessons

1. The freeze is a database state, not a grant state. On the reference night the application kept writing for three and a half hours through revokes and kill loops: grants were global, sessions opened before a revoke kept their rights, something restored grants twice, and a second application account was never on any list. The read-only attachment stopped every writer in minutes once it was used. Rule: Path A is the default freeze, proved by a write probe; the lockout is the fallback.
2. Enumerate every writer before the night. Accounts with write rights come from three privilege views and can be global, database or table grants; connected users come from sampling the process list. Rule: P3 captures accounts and sessions, the lockout snapshots every scope, and the writer watch runs with PROCESS from the start.
3. A watcher that samples once a minute misses fast single-row writes. Rule: the watch samples every 5 seconds and also compares row counts.
4. The switch ran out of order. Four statements were pasted from separate blocks under time pressure, ATTACH ... AS succeeded while the source was still attached (it made a branch instead of failing), and the original became reachable only by its storage id. Rule: the switch is a state machine whose every statement sits between checks, refuses anything out of order, addresses storage by STORAGE_ID, and attaches the retained copy before the live name.
5. Pipelines were not carried over. The inventory had redacted every literal, the copy account could not see pipelines, and the plan to read them live was dropped without a replacement. Rule: pipelines are part of the database; definitions are captured with the owner identity and a credentials placeholder, offsets are captured after the stop, and the switch refuses until the replay is verified.
6. Never hard-stop the copy. A killed runner held a leaf lock for 17 minutes. Rule: stop with the stop file or the deadline only; the rehearsal includes a kill test so the wait is known; a locked table has a fresh-table fallback.
7. Large varchar unique keys serialize inserts. Rule: a table that hits a lock wait is serialized and probed with a DELETE that matches no row and a short lock_wait_timeout.
8. Schema drifts during the day. Columns appeared between the morning capture and the window. Rule: the copy uses the inventory captured after the freeze and refuses definitions that differ.
9. Privileges were discovered one refusal at a time. Rule: P2 checks every privilege the runner needs, by name, before the night; the owner identity does grants, attachments and pipelines.
10. Verification has to fit the window. Per-bucket counts were too slow for billion-row tables and a count cannot see an in-place change. Rule: counts for all tables, newest values where a time column exists, grouped fingerprints within a time budget, and a verified-at time per table that the switch compares with the freeze time.
11. Commands must be unambiguous at 4 a.m. Rule: one ordered block per admin step, numbered steps with a pass or fail gate, warnings next to the step they belong to, and stop at the first failure with the observed state.
12. Keep the critical path on the kit's own connections. Tools that time out, lose their sign-in or reach only one aggregator cost hours. Rule: the kit drives the database through its own long-lived connections, or the owner notebook it generates, and journals every statement and gate.
